# Вопросы и решения: PaySnapper

Документация: https://docs.paysnapper.xyz/ (Payment API v5.7.2), разделы Payment API Basics, Payment Methods → Benin, Niger, Kenya, API Methods → Customer to the Business.

## Что уже уточнено у кассы

1. **Ссылка для redirect-операторов.** Ответ кассы: в ответе create её нет. Ссылка приходит запросом `status` в `extra.customer_redirect`, это шаг 3 блока «C2B for Provider_ids redirecting to Provider payment pages».
   Повторного вызова после create в движке нет (SCHEMA.md, «Чего в движке нет», п. 4), а метод `status` не входит в бриф. Поэтому для 835 (MTN Бенин) и 9564, 9562, 9563 (Нигер) create возвращает `Accepted` без ссылки, `Redirect` в конфиге не задан. Плательщику пока некуда идти. Чтобы эти методы заработали, движку нужен вызов `status` после create. См. кейс `payin redirect operator without link`.
2. **Обязательные `extra`.** Ответ кассы: только поля со звёздочкой в таблице своего `provider_id`. Соседние id не копировать. Если id нет ни в одном C2B-блоке, так и написать и поля не добирать.

   | Id | Блок C2B | Обязательные extra |
   | --- | --- | --- |
   | 836 Moov (Бенин) | нет ни в одном блоке | не добираем |
   | 835 MTN (Бенин) | redirect | `customer_email`, `customer_name`, `return_url` |
   | 10007 Celtiis (Бенин) | без OTP и редиректа | No Extra Required |
   | 9564, 9562, 9563 (Нигер) | redirect | `customer_email`, `customer_name`, `return_url` |
   | 292 M-Pesa, 293 Airtel (Кения) | нет ни в одном блоке | не добираем |

   Для 835 и Нигера поля обязательны, но отправить их нельзя. У движка нет подстановок для email, имени и return_url: из данных плательщика есть только `{clientPhone}`. Кроме того, тело create задаётся на всю секцию, а не на метод. В конфиг они не добавлены. **Вопрос к кассе:** что вернёт create для этих id без `extra`? Сейчас ожидаю отказ по валидации.

## Что неясно или противоречиво в документации

3. **`public_id` в пути.** Адрес вызова `https://api.paysnapper.xyz/{public_id}/payment_c2b`. Движок не допускает подстановку ни в `Path`, ни в `BaseUrl`. Значения у нас нет, регистрироваться не нужно. В конфиге стоит заглушка `PUBLIC_ID/payment_c2b`, её нужно заменить при подключении. **Вопрос:** выдайте `public_id` для `firm-a`. Он один на мерчанта или разный на окружения?
4. **Подпись колбэка лежит в теле, а не в заголовке.** Касса подписывает колбэк так же, как запрос, и кладёт подпись в поле `signature`. Движок проверяет подпись колбэка только из заголовка: при `Algorithm` не `None` загрузка требует `Header`. Значит, проверить её нельзя. Варианты:
   - выдумать заголовок — тогда все колбэки станут `Unknown`;
   - отключить проверку.

   Выбран второй: `Signing.PayinCallback.Algorithm = None`, причина записана в `Notes`. Это риск: колбэк можно подделать. Компенсация на стороне обработки — перед зачислением подтверждать итог запросом `status`. **Вопрос:** может ли касса продублировать подпись в заголовке? Есть ли список IP, с которых приходят колбэки?
5. **Сумма строкой «с двумя знаками после точки».** `amount` — строка формата `100.00`. Движок не умеет форматировать до двух знаков: `{sum}` даёт `1500` или `1500.5`, `{sum:minor}` даёт копейки. Решение:
   - отправлять `{sum}.00`;
   - на всех методах держать целую сумму через `AmountStep`. XOF — шаг 5 из документации. KES — шаг 1, то есть целые шиллинги: M-Pesa и Airtel Money в Кении работают в целых шиллингах.

   Сумма вроде `100.5 KES` отклоняется до вызова, а не уходит как `100.5.00`. **Вопрос:** принимает ли касса дробные KES? Нужен ли формат `.00` строго, или пройдёт `1500`?
6. **Id из брифа без лимитов.** Для 836, 292 и 293 в таблицах лимитов строк нет: там только суффиксные варианты. `MinAmount`/`MaxAmount` у этих методов не заданы, соседние строки не копировал. **Вопрос:** какие лимиты у 836, 292 и 293 на C2B?
7. **Формат номера.** Документация требует номер без `+`: `2290100000000`, `22700000000`, `254000000000`. Движок передаёт `{clientPhone}` как есть и не умеет вырезать `+`. **Вопрос:** примет ли касса номер с `+`? Если нет, нормализовать номер нужно до движка.
8. **Коды `result.code`.** В схеме перечислены `0, 1, 2, 3, 10201`, но описаны только `0` (OK) и `10201` (ошибка аутентификации). Ответы не-200 для платёжного API не описаны.
   - `10201` → `Error` `Api.Auth`, это наша ошибка конфигурации, а не отказ плательщику.
   - Остальные ненулевые коды → `Error` `Api.Rejected`.
   - HTTP не-2xx не попадает ни в одно правило → `Error` `Api.NoActionInResponse`.

   **Вопрос:** что значат коды 1–3? Какие HTTP-коды и тела бывают при ошибке валидации?
9. **Статусы.** Таблица Status Codes даёт `-1…6`. В `enum` ответа create указано `-1…4`, колбэка — `0…4`.
   - В create: `0, 1, 2` → `Accepted` (зачисление только по колбэку), `3, 4` → `Declined`, `-1` при `result.code = 0` → `Error`, потому что исход неизвестен.
   - В колбэке: `2` → `PaymentSucceeded`; `3, 4` → `PaymentFailed`; `0, 1, 6` → `NoAction`.
   - `-1` (undefined) и `5` (частичная отмена, только для POS) в карту не внесены. Они дают `Unknown` и уходят на ручной разбор, чтобы ничего не зачислить и не отменить вслепую.
   - `PaymentExpired` не используется: статуса истечения у кассы нет.

   **Вопрос:** есть ли у C2B таймаут подтверждения? Каким статусом он приходит, `3` или `4`?

## Доработка движка: шаг суммы

- Новое поле метода `AmountStep`: число в основных единицах, необязательное.
  - Ноль или отсутствие поля — шага нет, поведение остальных секций не меняется.
  - Отрицательное число или не число — ошибка загрузки.
- Проверка стоит в `MethodMatcher` после `MinAmount`/`MaxAmount`: `Sum % AmountStep == 0` на `decimal`, без плавающей точки.
- **Неподходящая сумма → `Declined` с кодом `Method.Rejected`, HTTP-вызова нет.** Так же движок уже отвечает на сумму вне границ. Почему не округлять:
  - плательщик подтверждает на телефоне сумму, которую видел. Если тихо отправить 1500 вместо 1502, сумма заказа и платежа разойдётся, и это всплывёт при сверке;
  - округление в какую-то сторону — решение продукта, а не адаптера. Отказ до вызова честно сообщает, что метод такую сумму не примет, и витрина может предложить ближайшую допустимую.
- Тесты на фикстуре `tests/fixtures/scheme.json`, без имени кассы, в `SchemeComponentTests`:
  - сумма на шаге уходит в HTTP;
  - сумма вне шага, включая дробную, отклоняется без вызова;
  - отрицательный или строковый шаг — ошибка загрузки;
  - ноль значит «шага нет».
- `docs/SCHEMA.md`: строка про `AmountStep` в разделе PaymentMethods, пункт «Шаг суммы на методе» убран из «Чего в движке нет».

## Замечания к самому движку (кодом не трогал)

- `{body:kv}` для вложенного объекта верхнего уровня всегда ставит префикс `result.`, а не имя объекта (`Signature.cs`, `AppendKvNode`). У кассы префикс — имя объекта (`extra.`, `provider_result.`). В нашем запросе вложенных объектов нет, на подпись это не влияет. Но если добавить `extra` или проверять подпись колбэка (`provider_result`), подпись разойдётся.
